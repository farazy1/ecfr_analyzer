Understanding the eCFR Analyzer

This page explains the purpose and function of each part of the eCFR Analyzer code. The project consists of a Python backend using Flask and a simple HTML front‑end powered by React. It downloads and processes federal regulations from the eCFR API—an API exposed by the eCFR website that allows clients to retrieve titles, chapters, parts and full text of regulations【360949012315245†L126-L133】. The front‑end displays aggregated statistics such as word counts and checksums.

Background Concepts

Content Delivery Networks (CDNs) are networks of proxy servers distributed across many geographic locations. They improve reliability and speed by caching content closer to users. Wikipedia describes a CDN as “a geographically distributed network of proxy servers and their data centers” whose goal is to provide high availability and performance【468032774274077†L175-L179】.

unpkg CDN is a specific CDN that serves files published on npm. It allows you to load JavaScript libraries directly from npm packages via a URL. For example, the unpkg home page notes that it is “a fast, global content delivery network for everything on npm”【772025400715672†L2-L7】. The front‑end uses this service to load React and ReactDOM without a build step.

Libraries and Technologies Used

This project uses a combination of Python and JavaScript libraries to provide server‑side functionality and a responsive web interface:

  • Flask – a lightweight Python web framework that routes HTTP requests to Python functions. It powers the /api/update and /api/summary endpoints.
  • flask_cors – a Flask extension that adds Cross‑Origin Resource Sharing (CORS) headers. Without it, the browser would block AJAX requests from the front‑end (served on one port) to the backend (on another port).
  • requests – a popular Python HTTP client library used to call the eCFR API and download XML and JSON data.
  • React – a JavaScript library for building user interfaces. The front‑end defines a small React component using modern hooks (useState, useEffect) to fetch data and render a table.
  • unpkg CDN – a content delivery network that serves React and ReactDOM straight from npm. The HTML file includes script tags that point at unpkg so no bundler or build step is required.
  • Python standard libraries – modules like json (for parsing JSON), hashlib (for computing MD5 checksums) and signal / atexit (for handling termination and logging) are used extensively in the backend.

Backend: ecfr_analyzer/backend/ecfr.py

This module encapsulates all logic for communicating with the eCFR API and computing metrics. It begins with imports:

  • hashlib — provides the md5 function for computing checksums.
  • json and re — used to handle JSON and regular expressions for cleaning text.
  • defaultdict from collections — a convenient dictionary subclass (not used in this version, but available).
  • typing — used for type annotations like Optional and List.
  • requests — a third‑party library that simplifies making HTTP requests.

The constant BASE defines the root path for all API calls, pointing to the eCFR versioner service. According to the SDK documentation, this service exposes endpoints like /titles.json, /structure/{date}/title-{title}.json, and /full/{date}/title-{title}.xml【360949012315245†L126-L133】.

Helper functions

  • _fetch_json(path) — concatenates the path to the BASE URL, performs an HTTP GET request, and parses the JSON response. If the request fails, it returns None. Encapsulating network calls in a helper allows for easy error handling.
  • _fetch_text(path) — similar to _fetch_json, but returns the raw text of the response. It is used to fetch XML documents for parts.
  • _collect_parts(node, parts) — recursively walks through a structural tree returned from the /structure endpoint. It looks for nodes where type == "part" and extracts the numeric part identifier. This is necessary because the hierarchy can contain subtitles, chapters and subchapters.
  • _extract_text(xml) — a very simple XML “parser” implemented with regular expressions: it strips out all tags by replacing anything between < ... > with spaces and collapses whitespace. Although not as robust as a real XML parser, it is sufficient for counting words.

build_dataset function

This is the core routine. It accepts three optional parameters:

  • selected_titles — allows the caller to process only certain titles; when None, all titles are processed.
  • log_progress and log_error — callbacks used by the Flask app to write progress and error information to log files.

The function performs the following steps:

  1. It requests the list of titles by calling /api/versioner/v1/titles.json. The returned JSON contains metadata like the title number, name, and the date each title is “up to date as of”【590897020559311†L0-L20】. That date is used to query the structure and full text of the title.
  2. It loops over each title. Reserved titles are skipped. If selected_titles is provided, only those numbers are processed. For each title it logs a progress message if log_progress is supplied.
  3. It fetches the list of versions (different historical snapshots) for the title using /versions/title-{num}.json. The length of the versions array becomes the version count metric.
  4. It fetches the hierarchical structure for the title at the relevant date via /structure/{date}/title-{num}.json. The top level of this structure contains children; the code iterates through those where type == "chapter". A chapter’s heading is treated as the agency name.
  5. For each chapter, it calls _collect_parts to gather all part numbers belonging to that chapter. It logs how many parts were found.
  6. It loops over each part number, fetching the full text with /full/{date}/title-{num}.xml?part={part}. If a request fails, the error callback logs contextual information. Otherwise the XML is stripped of tags and the number of words is counted.
  7. The text of every part in the chapter is concatenated. The code uses hashlib.md5 to compute a checksum of the concatenated text. It also counts how many times the word “shall” appears (case‑insensitive) and divides that by the total word count to produce a custom metric called shall ratio.
  8. A dictionary is appended to the dataset list containing the title number, title name, chapter identifier, agency name, word count, checksum, version count and shall ratio.

The result of build_dataset is a list of these dictionaries, one per chapter.

Saving and loading

The module also defines save_dataset(data, path) and load_dataset(path). These simply write and read the computed dataset to and from a JSON file on disk. Persisting the dataset avoids re‑downloading the entire CFR each time the server starts.

Backend: ecfr_analyzer/backend/app.py

This file defines the web API using Flask. In addition to wiring up routes, it now contains logic to handle incremental progress and graceful termination:

  • It imports Flask to create the app and flask_cors.CORS to allow the front‑end to make cross‑origin requests.
  • It defines several module‑level variables: a cache for the computed dataset, the path to data.json, and the paths to two log files (process.log and error.log) that live in the project root. It also introduces a boolean flag _update_in_progress which indicates whether a data download is currently underway.
  • Signal handlers for SIGINT (Ctrl‑C) and SIGTERM are registered. When the process receives one of these signals, the handler writes a line to error.log; if _update_in_progress is true, it notes that the termination occurred while an update was running. After logging, it exits the process. There is also an atexit hook: this runs when the interpreter is shutting down for any reason and writes a similar message to error.log if an update was in progress. This combination ensures that if you kill the server while it’s downloading data, you can see a message like “Process terminated by signal 2 during update” in error.log. Without this mechanism the process would just vanish and leave the log empty.
  • The /api/update route accepts both GET and POST requests. It can optionally take a ?title=## query parameter to limit the update to a single title; otherwise it processes all titles. At the start of an update, it clears the two log files and sets _update_in_progress to True. It loads any existing data.json to determine which titles have already been processed. It then loops through the list of titles; for each title that isn’t already present (or matches the query parameter) it calls build_dataset with a single‑title filter. After each title completes, it merges the new entries into the dataset, writes the entire dataset back to disk, and moves on. The try/except/finally in this route catches unexpected exceptions and logs them via the error callback, then clears _update_in_progress in a finally block so that the termination hooks know whether an update was running.
  • The /api/summary route returns the cached dataset. On first use it loads the dataset from disk if available. If a title parameter is passed, the returned list is filtered to entries whose title_number matches that parameter.
  • At the bottom of the file, a standard Flask if __name__ == '__main__' block starts the development server on port 5000.

Thanks to CORS, a web page served from another port (the front‑end) can make AJAX requests to these endpoints.

Front‑end: ecfr_analyzer/frontend/index.html

This HTML file builds a simple user interface without a build system. Some key parts:

  • The inline <style> block sets basic typography and table styling.
  • A paragraph explains that the data is computed from the eCFR API and cites the SDK documentation【360949012315245†L126-L133】.
  • The comments and script tags import React and ReactDOM from the unpkg CDN. As noted earlier, unpkg is a CDN that serves npm packages directly【772025400715672†L2-L7】. The script tags specify version 18 of React. These lines show the CDN in use in the front‑end source【520303780565026†L23-L26】.
  • The inline JavaScript defines a React component called MetricsTable. It uses React’s useState and useEffect hooks to fetch data from /api/summary when the component mounts. While the data is loading, it renders a “Loading…” message. Once the fetch resolves, it renders a table whose headers are fixed and whose rows are created by mapping over the JSON returned from the API.
  • Finally, ReactDOM.createRoot(...).render(...) attaches the component to the <div id="app"> element.

Because the front‑end fetches data from the Flask API, you need to run the Flask server at localhost:5000 before loading this HTML file in your browser.

How to Build and Run the Application

To use the eCFR analyzer locally you need to run both the Flask backend and the static front‑end. Here’s a step‑by‑step guide:

  1. Install dependencies. Ensure Python 3.8 or newer is installed. From a terminal change into the ecfr_analyzer/backend directory and install the required packages: 
    pip install flask flask_cors requests
  2. Start the backend server. Still in the backend directory, run: 
    python -m ecfr_analyzer.backend.app
    This command runs the app module in package notation, which ensures Python finds the package correctly. The Flask server starts on port 5000 and loads any existing data.json but does not download new data until you call one of its API endpoints.
  3. Trigger a download. To fetch all titles and build the dataset, send a request to /api/update. You can do this in a browser or with curl: 
    # fetch everything
curl -X POST http://localhost:5000/api/update

# fetch only a single title (e.g., Title 10)
curl -X POST "http://localhost:5000/api/update?title=10"
    Each call writes progress messages to process.log, errors to error.log and saves partial results to data.json after every title. If you interrupt the process, restarting it will resume where it left off.
  4. Retrieve metrics. Once some data has been downloaded, you can fetch the cached results via /api/summary: 
    # return the full dataset
curl http://localhost:5000/api/summary

# return only one title
curl "http://localhost:5000/api/summary?title=10"
    This endpoint returns JSON representing the list of chapters, and it is what the React front‑end uses to populate its table.
  5. Serve the front‑end. The front‑end is a static HTML file. You can open it directly or run a simple server. For example: 
    cd ecfr_analyzer/frontend
python -m http.server 8080
    It is important to start the static server from the directory that contains index.html; otherwise the file won’t be found. The commands above change into the frontend directory and serve its contents on port 8080. Then browse to http://localhost:8080/index.html. The updated page uses an absolute URL to fetch the data from http://localhost:5000/api/summary, so it will work even though the HTML and API are on different ports.

Following these steps allows you to run the complete system and, if desired, interact with the API from scripts using the curl commands shown above.

How Everything Fits Together

When you call /api/update on the Flask server, it downloads each title’s structure and parts from the eCFR API, computes the metrics, logs its progress to process.log and any errors to error.log, and stores the results in data.json. When you open index.html (ideally via a small static server), React fetches the dataset from /api/summary, builds a table, and displays it. The unpkg CDN supplies the React libraries needed by the page【772025400715672†L2-L7】, and the CDN concept explains why this works efficiently【468032774274077†L175-L179】.

The server now writes its progress after every title, so you can interrupt an update at any time without losing work. When restarted, it reads data.json and skips titles that are already present. A title query parameter on /api/update or /api/summary lets you download or view just one title instead of the entire CFR.

Understanding index.html and the Page Load Process

The front‑end is written in standard web technologies: HTML for structure, CSS for styling and JavaScript for behaviour. When you navigate to http://localhost:8080/index.html in your browser, several things happen:

  1. The browser sends an HTTP GET request to the static server started with python -m http.server. Because you ran that command in the frontend directory, the server finds index.html and returns its contents.
  2. The browser starts parsing the HTML. It applies the inline <style> rules to set fonts and table styling.
  3. When the parser encounters the two <script src="https://unpkg.com/..."> tags, it pauses parsing and requests those JavaScript files from the unpkg CDN. This is the moment when the CDN is contacted. The CDN delivers minified versions of React and ReactDOM, which are cached by your browser for subsequent visits.【772025400715672†L2-L7】
  4. After React and ReactDOM load, the browser continues to the inline script. This script defines a React component called MetricsTable. Using React’s hooks, it initially renders a “Loading…” message and then, once the component mounts, calls fetch('http://localhost:5000/api/summary') to request the dataset from the Flask backend.
  5. The call to fetch sends an HTTP GET to the backend running on port 5000. Because CORS is enabled, the browser accepts the response even though it’s from a different origin. When the JSON returns, the component updates its state and React re‑renders the table rows.

In short, the HTML file itself does not contain any data. It pulls React from a CDN, executes JavaScript to fetch the metrics from your backend, and then renders them dynamically. If either the CDN is unreachable, the backend is not running, or the file is opened without a web server (e.g., via file://), the table will remain empty.

Explaining the Table Columns

Once the data is fetched, the React component renders a table where each row corresponds to a single chapter (treated as an agency) within a title. The columns have the following meaning:

  • Agency – the name of the chapter, typically describing the agency or sub‑agency responsible for that portion of the CFR. It comes from the heading field of the eCFR structure API.
  • Title – a combination of the CFR title number and its full name (for example, “10 – Energy”). Titles group related regulations; there are 50 titles in the CFR.
  • Chapter – the chapter identifier (usually a Roman numeral or letter) within the title. Chapters further subdivide the title.
  • Word Count – the total number of individual words across all parts within the chapter. The backend computes this by fetching each part’s text, stripping out XML tags, splitting on word boundaries and summing the lengths.
  • Checksum – an MD5 hash of the concatenated text from all parts in the chapter. This acts as a fingerprint: if the regulatory text changes, the checksum will change too.
  • Versions – the count of historical versions available for the title. The eCFR API exposes a /versions endpoint listing snapshots; the length of that list is used as a proxy for how often the title has been updated over time.
  • Shall Ratio – the frequency of the word “shall” relative to the total word count in the chapter. The backend counts how many times the case‑insensitive word “shall” appears and divides by the total number of words. This gives a small number (e.g. 0.012345) indicating how directive the language might be.
